# AI26 recovery status: issues #396, #400 and #401

## #396: Allas quota (operator action still required)

The quota outage has a merged ingest mitigation: records reach Mongo even when the raw-object PUT fails, and the pending raw object is explicitly marked. This does **not** grant new S3 capacity or recover the historical lost captures. Follow [AI26_ALLAS_QUOTA_RECOVERY.md](AI26_ALLAS_QUOTA_RECOVERY.md) on the authorized host. **Do not delete any raw objects without an explicit retention decision.** Verify both `PutObject` and subsequent recovery of pending raw captures before declaring the outage resolved.

## #400: recurring non-browser polling

The current main implementation provides stable manifest identities and configurable polling cadence (default one hour), with due jobs rearmed through `rearm_due()`. The current implementation also permits failed jobs to become eligible when due, and `cancel_missing()` affects all job kinds, including running leases. These operational differences from the original PR need explicit review before deploying a shared browser/non-browser queue. Operator verification: observe a previously done web/Bluesky/Mastodon job claimed again after the cooldown, then check new records by capture date (not only publication date). The historical gap is not repaired automatically.

## #401: X producer versus replay

`ai26_x_bridge.py` is a replay consumer of local captures, **not an X producer**. The browser capture launcher already exists at `scripts/start_ai26_x_capture.sh` and needs an authorized Firefox session on the researcher workstation; do not start it on Laskin or bypass access controls.

The Laskin collection wrapper now runs the read-only freshness check on each scheduled cycle, using MongoDB capture provenance timestamps on `spectacleScraper.ai26__records` rather than a publication timestamp. To check manually on a configured host:

```bash
python scripts/check_ai26_capture_freshness.py --platforms x --max-age-hours 24
```

Missing X records, missing Mongo config, future timestamps and stale captures produce a nonzero status and an alert. The existing checker retains its `--captures-json` mode. The wrapper **does not stop RSS ingestion** when X is stale. This is monitoring, not proof of an operational browser capture pipeline. The remaining deployment decision is to authorize, schedule and validate real fresh X capture on a browser-capable workstation or explicitly declare the stratum closed for Phase 1. Neither replay nor synthetic timestamp updates count as evidence of capture.

## Validation requirements before closing issues

- Verify the real shared queue transitions across two hourly cycles; ensure inactive scholarly backends do not retry and the X browser queue is untouched.
- Verify the alert appears in the next Laskin collection log when X is stale.
- For #396, obtain successful Allas writes or documented capacity restoration.
- For #401, verify a new authenticated X capture produced by the authorized browser (or document the explicit closure decision).
